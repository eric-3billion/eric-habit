# 00 · 의도 드러남 / 예측가능성 (최우선)

가장 싫어하는 것: **의도가 안 드러나는 코드, 예측 불가능한 코드.**

- 훅/함수/모듈 이름이 **반환값·동작을 정직하게 telegraph**해야 한다.
  - 예: `const [user, setUser] = useCurrentUser()` — 이름만 봐도 반환·동작이 뻔히 읽힘.
- innocent한 이름 뒤에 **숨은 부수효과/surprise 금지** (principle of least astonishment).
- **도메인 모듈·함수 단위로 의도를 표면화.** `format*`인데 분류/판정 로직을 숨기거나, `*Identity` 같은 거울 state처럼 왜 존재하는지 이름이 설명 못 하는 것 금지.
- **매직값·센티넬**(`-1`=N/A, `""`=unknown 등)은 네이밍 또는 주석으로 의미가 드러나게. 단 이름을 붙이는 데서 끝이다 — 그 이름을 산술에 섞으면 거짓이 된다(아래 「이름이 거짓이 되는 두 자리」).

## 체크 질문

> 이 이름만 보고 동작·반환·부수효과를 예측할 수 있는가? 아니면 개명하거나 분해한다.

## 진단 — 의도가 안 드러날 때 나오는 증상 4종

표면이 달라도 같은 병이다: **코드가 의도를 못 드러내서 다른 수단이 대신 떠맡은 것.** 처방은 그 표면을 다듬는 게 아니라 구조를 고치는 것이다.

| 증상 | 실제 병 | 처방 |
|---|---|---|
| 설명 주석이 길어진다 | 이름·타입이 의미를 못 담음 | 파생값에 **이름**을 붙이거나 타입으로 좁힌다 |
| 몸통에 복잡한 삼항이 낀다 | 그 함수가 두 일을 함 | **쪼갠다**([01 §1](01-component-design.md)) |
| 정직한 이름이 안 떠오른다 | 경계가 틀림 | 이름을 짜내지 말고 **분해**한다 |
| 이름이 정확한데 "뭐하는 놈인지 모르겠다" | 수식어를 압축·축약함 | 분해하지 말고 **펼쳐서 개명**한다 (아래) |

- **주석이 길어졌다는 것 자체가 신호다.** 내용이 정확한 주석이어도 **길면** 그 자리의 코드가 안 읽힌다는 뜻이다.
  - 단 이건 *설명* 주석에 대한 진단이다. **코드로는 볼 수 없는 제약**(호출 맥락 가정, 의도적 복제, 연동 지점)은 길어도 남긴다 — 그건 코드가 대신할 수 없다([canonical-examples](canonical-examples.md) `useProjectId`, [01 §7](01-component-design.md)).
- **4행은 처방이 반대다.** 1~3행은 구조를 고치라는 신호지만, **이름이 이미 있고 정확한데 안 읽히는** 것은 경계 문제가 아니라 **어휘 문제**다 — 여기서 분해하면 엉뚱한 데를 고친다. 처방은 개명이고 방향은 **펼치기**:
  - **주체 + 판정 기준을 다 쓴다** — `checkAffordableSelection`(형용사로 압축) → `checkSelectionWithinBudget`(무엇을 · 무슨 기준으로).
  - **도메인 수식어는 길어져도 축약하지 않는다** — `hasMethodChoice` → `hasShippingMethodChoice`.
  - **낯선 단어·전치사 꼬리를 쓰지 않는다** — `furthestStep`·`statusOf`·`completedUpTo` 대신 흔한 단어 여럿으로.
  - 한 단어로 안 되면 **여러 단어를 쓴다.** 위 "주석이 길면 신호"는 *주석* 얘기이지 이름을 짧게 하라는 뜻이 아니다.
- 제너럴한 이름(`*Query`·`*Info`·`*Data`·`*Config`)은 축 경계를 무너뜨린다([02-structure-cohesion](02-structure-cohesion.md)). 반대로 **과하게 구체적인 이름도 축 오류**다 — 같은 곳에 양방향으로 적혀 있다.
- 한 자리를 고쳤으면 **같은 증상을 레포 전체에서 훑는다** — 이 병은 한 군데서 끝나지 않는다.

## 이름의 형태 — 이웃·접미사·어휘가 정확성보다 먼저 읽힌다

위 룰들은 **한 이름이 개별적으로** 정직한지를 본다. 그런데 개별적으로 정확한 이름이 **놓인 자리** 때문에 실패하는 경우가 따로 있다.

### 형제 이름은 포맷을 공유한다 — 단위를 접미사에 박는다

개별적으로 정확한 이름도 **이웃과 어긋나면 형제인지 안 읽힌다.** 한 모듈·인접 인터페이스에서 같은 개념을 가리키는 값은 **같은 어휘·같은 접미사 포맷**으로 쓴다 — 새 값을 도입할 때 이름을 지어내지 말고 **옆에 이미 있는 이름의 포맷을 따른다.**

- **단위를 접미사에 박는다** — `Index`(0-based 위치) vs `Count`(개수)는 단위가 달라, 이름에 없으면 둘을 섞은 산술이 조용히 통과한다(아래 센티넬 절).
- **통일할 포맷은 취향이 아니라 소비 경계가 정한다.** 그 값을 받는 쪽이 index 로 받으면 index 다.

```ts
// ❌ 같은 "스텝 위치"인데 어휘·단위가 다 다르다
lastReachedIndex   // 소비처(Stepper)가 받는 이름
completedUpTo      // 전치사 꼬리, 단위 불명
validPrefix        // 압축 표현, 단위 불명
filledStepCount    // 여기만 개수
// ✅ 소비 경계(index)에 맞춰 통일
lastVisitedStepIndex / progressLimitStepIndex / valueLimitStepIndex
```

**왜** — 형제로 안 보이면 `min()` 하나로 합쳐도 되는 값들을 각자 다른 것으로 취급하고, 단위 혼동은 타입으로도 안 잡힌다. (값 *표현*의 일원화는 [05-types](05-types.md) 「도메인 규약 일관성」 — 이 절은 식별자 *포맷*이다.)

### 접미사는 "어떤 종류·어느 위계"라는 주장이다

`Modal`/`Dialog`/`Module`/`Wrapper` 같은 타입 접미사는 그것이 **어떤 종류의, 어느 위계의 것**이라는 주장이다. 둘 다 개별적으로 정직해도 **쌍으로 놓이면** 실패할 수 있다.

- 중첩·형제 레이어를 **동의어**로 가르면 접미사가 정보를 0비트도 안 싣는다 → 각 조각의 **실제 역할**(가드·셸 / 경계·몸통)을 이름에 담는다.
- 위계가 다른 것에 같은 접미사를 붙이면 **잘못된 동렬 주장**이 된다 → 개명하고, 정말 위계가 다르면 자료구조도 가른다.

```tsx
// ❌ 둘 다 "진짜 모달"이라 각각은 정직한데, 쌍이 말장난이 된다
<OrderDetailModal> <OrderDetailDialog /> </OrderDetailModal>
// ✅ 역할이 이름에 — URL 가드 셸 / 경계를 가진 몸통
<OrderDetailRoute> <OrderDetailDialog /> </OrderDetailRoute>

// ❌ 보증은 부속 옵션인데 코어 모듈들과 같은 접미사로 동렬을 주장
type Module = CpuModule | RamModule | WarrantyModule;
// ✅ 위계가 다르면 접미사도, 자리도 다르다
type Module = CpuModule | RamModule;  type Addon = Warranty;
```

### 이름은 이 제품의 공용 어휘로 읽혀야 한다

동작에 정직하고 충분히 구체적이어도, **그 단어가 이 제품에서 먼저 읽히는 뜻**이 다르면 틀린 이름이다. 검증 순서는 "동작이 맞나" **이전에** "이 단어를 독자가 무엇으로 먼저 읽나".

- **UI 은유**: `gauge`(계량기) → `UsageBudget`. 화면 위젯 어휘가 도메인 값 이름으로 스며든 것.
- **설계자 내부 은어**: `PRODUCT_AXES` 의 "축" → `PRODUCT_ATTRIBUTES`. 설계할 때 쓴 메타포는 코드에 남기지 않는다.
- **다른 도메인 의미와 충돌하는 단어**: 과금 화면의 유니온 태그 `"free"`(뜻은 "둘 다 가능")는 "무료"로 먼저 읽힌다 → `"both"`. **태그 값도 이름이다.**

## 이름이 거짓이 되는 두 자리 — 낡은 그릇 이름, 산술에 섞인 센티넬

아래 안티 예시들은 **처음부터 틀린** 이름이다. 그런데 **지을 때는 맞았는데 나중에 거짓이 되는** 이름이 따로 있고, 이건 새 코드 리뷰로는 안 잡힌다.

### 리팩터가 내용을 줄이면 그릇 이름도 줄인다

**그릇을 주장하는 이름**(`*Config`·`*Context`·`*Options`)은 내용이 하나로 좁혀진 순간 **그 하나를 이름에 박는다.** 이름이 없어진 내용을 계속 광고하면 소비처가 있는 줄 알고 찾는다.

- **트리거는 삭제·이동을 한 직후다** — 뺀 자리의 이름이 아직 뺀 것을 주장하고 있는지 본다. [cases/viewport-clamp-derivation](cases/viewport-clamp-derivation.md) 의 "주석이 거짓말하기 시작하면"의 **이름 버전**이다.

```ts
// ❌ label 이 STEP_LABELS 로 빠져 스키마만 남았는데 이름은 여전히 "여러 개를 담는다"고 주장
createOrderStepConfig(): { schema: ZodType }
// ✅ 남은 하나를 이름에 박는다 (파일명도 함께)
createOrderStepValidators(): { schema: ZodType }
```

### 센티넬에 이름을 붙였으면 그 이름은 "없음" 하나만 뜻한다

- **산술 항으로 쓰지 않는다.** 이름 붙은 센티넬을 오프셋으로 재사용하면 이름이 거짓이 되어 **상수화가 매직넘버보다 나빠진다.**
- 그런 산술이 필요해졌다는 건 이름이 부족한 게 아니라 **표현이 틀렸다는 신호**다 → 잘 명명하는 대신 **센티넬이 존재하지 않는 표현으로 갈아탄다.**

```ts
// ❌ -1 을 상수로 뽑았더니 그 상수를 오프셋으로 재사용 — "없음"이 아니게 된다
const NO_FILLED_STEP = -1;
return NO_FILLED_STEP + filledStepCount;
// ✅ 개수로 표현하면 센티넬 자체가 사라진다 (상수도 같이 지운다)
return filledStepCount;   // 0 = 아직 없음
```

## 안티 예시 (실제로 걸렸던 것)

- `queryIdentity` — "정체성"이라는데 실제론 *이전 쿼리 거울 state*. 이름이 존재 이유를 설명 못 함.
- `formatScore(-1 → "N/A")` — `format`인데 *결측 판정*을 숨김.
- `data-has-query` — DOM에 박힌 의도가 불명(읽는 곳도 없음).
- `isInteractiveRowClick` — "인터랙티브"의 정의가 셀렉터 안에 숨어 예측 불가.

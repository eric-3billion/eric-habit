# eric-refine — 기준 통과까지 개선 루프

작업 중인 코드를 Eric의 코드 습관에 수렴시킨다. **습관 룰은 이 스킬에 두지 않는다 — `habits/`(SSOT)를 읽어서 적용한다.** 이 문서는 *루프 절차와 종료 조건*만 담는다.

핵심: **루프는 쉽고 수렴이 어렵다.** 이 스킬의 가치는 "다시 봐"가 아니라 **언제 멈추는지(gate)·무엇을 안 고치는지(브레이크)**다. 종료를 선언할 수 있는 건 오직 **아무것도 고칠 게 없었던 전면 심사 라운드**뿐이다 — 수정한 라운드는 종료 라운드가 될 수 없다.

## eric-review 와의 분업

- **eric-review** = PR 리뷰(gh 스냅샷 기반, 코멘트 게시, 수정 안 함). **eric-refine** = 로컬 working tree 개선(수정 실행, 게시 없음). 대상이 PR이면 eric-review 로 보낸다.
- 렌즈 ↔ habit 매핑은 eric-review 와 **의도적으로 복제**돼 있다 — 스킬 문서끼리 참조시키면 한쪽만 읽고 절차를 반쪽으로 수행하게 되고, 매핑만 공용 파일로 빼기엔 5줄짜리다. **한쪽을 바꾸면 eric-review 의 매핑도 맞출 것.**
  - `intent` → `00-intent.md` (최우선)
  - `component` → `01-component-design.md`, `02-structure-cohesion.md`, `03-composition.md`
  - `functional` → `04-functional-domain.md` (+ `canonical-examples.md`)
  - `types` → `05-types.md`
  - `test` → `06-testing.md`
  - `correctness` → (습관 아님) 일반 정확성/React 품질

## 절차

1. **대상 확정** — `$ARGUMENTS`에 경로/글롭이 있으면 그 파일들. 없으면 `git diff HEAD --name-only` + untracked 중 코드 파일 = "이번 작업분". **작업분 밖 파일은 맥락으로 읽되 절대 고치지 않는다**(blast radius — 기준 통과를 명분으로 한 스코프 크리프 금지).

2. **루프** — 아래 a→d 가 한 라운드다. **통과(c) 또는 상한(3번)에 닿을 때까지, 라운드 사이에 사용자에게 돌아오지 않고 계속 반복한다.** 질문 목록도 라운드마다 묻지 말고 모아서 종료 보고에서 한 번에.

   - **a. 전면 심사** — 매 라운드 라운드 1과 동일한 강도로: 해당 렌즈의 habit 파일(`~/code-style/habits/00~06`)을 기준 삼아, 대상 파일 **본문을 다시 Read** 해(수정본이면 diff 가 아니라 파일로 — 신선한 눈) 6렌즈로 훑는다. **전면 = 대상 전체 커버다.** 대상이 커서 한 번에 못 읽으면 여러 패스로 나누되 **그 패스 전부가 한 라운드다** — 커버리지를 라운드들에 걸쳐 분할하지 말 것(실측: 33파일 대상에서 "아직 안 본 파일부터" 식으로 쪼갰더니 라운드 1~4가 사실상 초독에 소진돼 상한을 태웠다. 라운드 N에서 처음 읽는 파일이 나오면 그건 재심사가 아니라 라운드 1이 안 끝난 것이다). 발견마다 심각도(blocker/high/medium/low/nit)·`파일:라인`·근거. eric-review 5번과 같은 정신으로 **적대적 자기검증**(해당 라인 다시 열어 확인, 추측·환각이면 버림). 단 이전 라운드에서 "묻는다/버린다"로 판정한 항목은 새 근거 없이 재상정하지 않는다 — 판정 뒤집기 반복은 위장된 무한루프다.
   - **b. 3분류** — 검증 통과한 발견을 셋으로 나눈다. 이 분류가 셀프 채점 편향의 방어선이다:
     - **고친다** — 룰 위반이 명확하고 수정이 안전한 것(동작 불변이거나 타입/테스트가 받쳐줌).
     - **묻는다** — 저자 판단 영역: 트레이드오프, rule of three 미충족 추출, 설계 방향 변경. **고치지 않고** 질문 목록에 적립. "위반"으로 몰아 맘대로 고치는 것 금지.
     - **버린다** — 오탐, 이론적 nit. 한 줄 사유와 함께 종료 보고에 투명하게.
   - **c. Gate(종료 조건)** — 이번 심사의 "고친다"가 **0건이면 통과, 루프 종료.** 게이트는 **심사 결과에만** 걸린다: **"방금 고쳤으니 해소됨"으로 0건을 선언할 수 없다.** 수정이 일어난 라운드는 절대 종료 라운드가 될 수 없고, 반드시 다음 라운드의 전면 심사가 클린해야 통과다. "묻는다"와 low/nit 는 게이트를 막지 않는다(이게 수렴 장치다). **게이트를 통과시키려고 심각도·분류를 하향 조정하는 것 금지** — 목표는 통과 선언이 아니라 기준 충족이다.
   - **d. 수정 + 기계 검증** — "고친다"만 실행. **수정 자체가 새 위반을 만들면 하지 않는다** — 얕은 포장·표본 1개 추출·축 오염을 *만들면서* 다른 룰을 통과시키는 건 안 고친 것만 못하다(habits 03의 브레이크는 수정 행위에도 적용). 프로젝트에 typecheck/lint/test 스크립트가 있으면 대상 범위로 실행, 깨지면 해당 수정을 되돌리고 "묻는다"로 강등(왜 단순 수정이 안 되는지 메모). → **다음 라운드 a 로 돌아간다.**

   > **왜 이 구조인가** — 초판은 "라운드 2+는 이전 발견 해소 확인만"으로 심사를 축소했더니, 실전에서 수정 후 재심사 없이 **라운드 1 만에 통과를 선언하고 멈췄다.** 종료를 선언할 수 있는 건 클린한 전면 심사뿐이고, 루프는 그게 나올 때까지 돈다. 수렴은 심사 범위 축소가 아니라 **"고친다"의 문턱**(명확한 위반 + 안전한 수정만 게이트에 카운트)이 만든다. 이 라운드 축소를 되살리지 말 것.

3. **라운드 상한: 10** (사용자가 명시하면 그 수). 상한 도달 시 멈추고 남은 발견을 보고한다 — 10라운드에 수렴 안 하는 발견은 거의 확실히 저자 판단 영역이거나 오탐이니, 루프를 늘리는 게 아니라 분류를 의심할 것.

4. **종료 보고** — 라운드별 고친 것(`파일:라인`), 되돌린 것, 버린 오탐(한 줄 사유), **질문 목록**(저자 판단 영역 — 각각 트레이드오프 요약과 함께), 통과/미통과와 소요 라운드 수. **커밋하지 않는다** — diff 확인과 커밋은 사용자 몫.

## 하지 말 것

- 작업분 밖 리팩토링 (아무리 눈에 밟혀도 — "추가 관찰"로 보고만)
- 자동 커밋
- **수정한 라운드에서 통과 선언** (재심사 없는 종료 — 실측된 실패 모드)
- 라운드 사이에 멈춰 사용자에게 확인받기 (질문은 종료 보고에 모아서)
- 게이트 통과 목적의 심각도·분류 하향
- "묻는다" 항목을 임의로 고치기 (저자 판단 선점)
